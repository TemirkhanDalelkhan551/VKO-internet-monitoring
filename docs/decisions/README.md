# Архитектурные решения

Каталог предназначен для решений, которые меняют границы компонентов, модель хранения, протоколы, безопасность или эксплуатацию и требуют ответа на вопрос «почему сделано именно так».

На момент создания каталога отдельные ADR в репозитории отсутствуют. Существующие решения нельзя ретроспективно объявлять принятыми без подтверждения контекста и рассмотренных альтернатив. Их текущее фактическое состояние описано в [обзоре архитектуры](../architecture/overview.md), [модели безопасности](../security/security-model.md) и [техническом долге](../technical-debt.md).

## Когда создавать ADR

ADR нужен, если изменение:

- заменяет PostgreSQL, файловую очередь или способ серверной идемпотентности;
- меняет аутентификацию устройств либо пользователей;
- вводит новый внешний сервис или передаваемые ему данные;
- меняет схему развёртывания, обновления или резервного копирования;
- создаёт значимый компромисс безопасности, доступности или совместимости.

Мелкие реализации endpoint, UI-изменения и обычные исправления ошибок ADR не требуют.

## Правила ведения

1. Скопировать [ADR-TEMPLATE.md](ADR-TEMPLATE.md) в `ADR-NNN-краткое-название.md`.
2. Присвоить следующий последовательный номер.
3. Заполнить только подтверждённые варианты и последствия.
4. После принятия не переписывать историю решения; изменение оформлять новым ADR со ссылкой на заменённый.
5. Добавить запись в индекс ниже.

## Индекс

Принятых ADR пока нет.
