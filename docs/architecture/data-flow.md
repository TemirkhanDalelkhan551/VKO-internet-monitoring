# Потоки данных

Документ фиксирует основные потоки, которые прослеживаются от текущих worker-процессов и HTTP endpoints до репозиториев. Названия полей и ограничения запросов приведены в [API.md](../API.md).

## Активация устройства

1. Administrator или Regional создаёт школу и линию, затем запрашивает одноразовый код через пользовательскую Bearer-сессию.
2. API сохраняет хэш кода, срок действия и привязку к школе/линии. Открытый код возвращается один раз.
3. Setup выполняет preview кода без его расходования и показывает оператору найденную привязку.
4. После подтверждения Setup отправляет код, устойчивый идентификатор компьютера и сведения устройства.
5. API атомарно расходует код, создаёт устройство и возвращает Device ID, School ID, Line ID и новый токен.
6. Setup записывает конфигурацию, защищает токен Windows DPAPI, ограничивает доступ к файлу и запускает службу.
7. При прерывании локальной фиксации повторная активация тем же кодом разрешена ограниченное время только тому же компьютеру; прежний токен заменяется.

Секрет устройства не должен передаваться через URL, журналы или пользовательскую веб-сессию.

## Измерение и доставка

```text
DailyMeasurementSchedule или локальный file trigger
  -> SystemLoadGuard
  -> MeasurementCollector
  -> latency + download + upload + network context
  -> InternetMeasurement с новым EventId
  -> JsonFileMeasurementOutbox
  -> OutboxDispatcher + DispatchRetryPolicy
  -> POST /api/measurements
  -> device authentication + validation
  -> IMeasurementRepository
  -> PostgreSQL или JSON
  -> оценка состояния и инцидента
```

До измерения агент проверяет загрузку CPU и фоновую сетевую активность. После достижения максимального времени откладывания измерение всё равно выполняется, чтобы не прерывать наблюдение.

При сетевой, rate-limit или серверной ошибке файл остаётся в очереди. Повтор выполняется с растущей задержкой и jitter. Отклонённый из-за неисправимого payload (`400`, `413`, `422` без `Retry-After`) замер сохраняется в quarantine, после чего dispatcher продолжает очередь. Для замера из будущего API возвращает `Retry-After`, поэтому агент сохраняет его в очереди. Повреждённые локальные записи также изолируются; размер очереди ограничивается конфигурацией. API использует `EventId` для идемпотентности, поэтому повторная доставка не создаёт вторую запись.

В ограниченном JSON-режиме API сериализует замер в уникальный временный файл с `WriteThrough`, закрывает его и атомарно переименовывает в `{EventId}.json`. Параллельная запись того же `EventId` считается дубликатом только после появления готового файла.

## Heartbeat и удалённое расписание

1. `HeartbeatWorker` периодически отправляет идентификаторы привязки, время и версию агента.
2. API проверяет токен и точное совпадение School ID, Device ID и Line ID.
3. Сервер сохраняет время последней связи и возвращает рабочие окна измерений.
4. Агент применяет только корректный непустой набор окон; при неверном ответе сохраняет прежнее расписание.

Heartbeat и свежесть последнего измерения являются разными показателями.

## Инвентаризация оборудования

После запуска `HardwareInventoryWorker` один раз собирает аппаратные сведения, сначала сохраняет их в отдельную локальную очередь, а затем повторяет доставку до принятия API. Чтение инвентаризации через административный API скрывает чувствительные подробности для ролей, которым они не нужны.

## Пользовательская веб-сессия

1. Пользователь отправляет login/password в `/api/auth/login`.
2. API проверяет пароль, ограничения попыток и блокировку, создаёт случайный session token и сохраняет только его SHA-256-хэш.
3. Web UI хранит Bearer-токен в памяти и отправляет его в `Authorization`.
4. `UserAccessMiddleware` аутентифицирует сессию, формирует разрешённые линии и проверяет роль, путь и область до выполнения endpoint.
5. Для защищённых запросов API пишет начало аудита до изменения и результат после ответа.
6. Logout, смена пароля, роли, области или блокировка делают соответствующие сессии недействительными.

## Автоматические инциденты и Telegram

После сохранения измерения сервер оценивает последовательность сигналов линии. Подтверждённая проблема открывает инцидент, подтверждённое восстановление переводит его в восстановленное состояние. Создание ручного инцидента также может поставить уведомление в очередь.

Telegram-доставка выполняется после фиксации инцидента через ограниченную очередь в памяти. Сбой Telegram не откатывает измерение или инцидент, но недоставленное сообщение теряется при переполнении очереди или перезапуске процесса.

## AI-черновик обращения

По явному запросу авторизованного пользователя API читает инцидент и доступные измерения, формирует ограниченный набор фактов и отправляет их OpenAI-compatible provider. В запрос входят названия школы, линии и поставщика, номер, тип и описание инцидента, время, количество результатов и агрегированные метрики. Ответ является только редактируемым черновиком; автоматической отправки поставщику нет.

При выключенной конфигурации, таймауте или отказе провайдера основной контур мониторинга и ручное обращение продолжают работать.
