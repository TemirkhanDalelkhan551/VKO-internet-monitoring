# Стратегия тестирования

Цель проверок — подтвердить доменные правила, надёжность at-least-once доставки, серверную идемпотентность по `EventId`, границы ролей и критические пользовательские сценарии. Текущие исторические счётчики запусков находятся в [PROJECT_SNAPSHOT.md](../PROJECT_SNAPSHOT.md); этот документ описывает воспроизводимый подход, а не фиксирует число тестов.

## Уровни проверок

| Уровень | Расположение | Что подтверждает |
| --- | --- | --- |
| .NET-тесты | `tests/VkoMonitoring.Agent.Tests` | Расписание, повторы, очереди, валидацию, измерения, активацию, роли, инциденты, отчёты, рейтинг, setup и вспомогательные API-компоненты. |
| Web model tests | `tests/web/*.test.mjs` | Чистые преобразования UI: фильтры, периоды, графики, статусы, доступность действий и обработку отсутствующих данных. |
| Интеграционные PowerShell-сценарии | `scripts/verify-*-integration.ps1`, `scripts/verify-web-*.ps1` | HTTP-контракты, PostgreSQL, области ролей, отчёты, карту, справочники, активацию и инциденты в изолированном контуре. |
| Проверки артефакта | `scripts/verify-installer.ps1` | Имя, версия, минимальный размер, SHA-256 и при необходимости подпись/timestamp установщика. |
| Эксплуатационные проверки | `scripts/verify-postgres-restore.ps1`, health endpoints | Восстановление резервной копии и готовность API/хранилища. |
| Ручная приёмка | `docs/DEMO_CHECKLIST.md`, `docs/USER_ACCESS_TESTING.md` | Реальный Windows EXE, браузерные роли, внешний стенд и сценарии, которые нельзя достоверно покрыть локальным unit-тестом. |

## Базовая локальная проверка

Из корня репозитория:

```powershell
dotnet restore .\VkoInternetMonitoring.sln
dotnet test .\VkoInternetMonitoring.sln --configuration Release
dotnet build .\VkoInternetMonitoring.sln --configuration Release --no-restore

$tests = Get-ChildItem .\tests\web\*.test.mjs | ForEach-Object FullName
node --test $tests
```

Сборка выполняется с nullable, актуальным анализом и `TreatWarningsAsErrors=true`. Успех означает ноль ошибок, предупреждений, упавших и неожиданно пропущенных тестов.

## Интеграционные сценарии

Интеграционные скрипты используют отдельные локальные базы и опубликованные каталоги в `artifacts`. Перед запуском необходимо прочитать заголовок и параметры конкретного скрипта. Их нельзя направлять на рабочую базу Render.

Основные сценарии:

- `verify-api-integration.ps1` — общий API, авторизация, роли, измерения и жизненный цикл;
- `verify-directory-integration.ps1` — школы, линии, контакты и договоры;
- `verify-map-integration.ps1` — координаты и области данных;
- `verify-report-integration.ps1` — CSV/XLSX и фильтры;
- `verify-web-activation.ps1` — выдача, preview, активация и отзыв кода;
- `verify-web-incidents.ps1` — ручные и автоматические инциденты;
- `verify-render-roles.ps1` — только read-only проверка пяти ролей на настроенном внешнем стенде.

Тестовые учётные данные допустимы только для локальных fixtures. Рабочие логины и пароли передаются через переменные среды и не должны выводиться в лог.

## CI

`.github/workflows/ci.yml` запускает два независимых job. Windows runner выполняет restore, Release build, .NET-тесты, Node.js-тесты, аудит известных уязвимостей NuGet-зависимостей и синтаксический разбор PowerShell-скриптов. Linux runner поднимает PostgreSQL 17 через Docker Compose и запускает `verify-api-integration.ps1` в изолированной базе. Workflow запускается для push и pull request и имеет только `contents: read`.

CI не заменяет проверку подписанного EXE, реальную установку Windows-службы, браузерную accessibility-приёмку и проверку внешних провайдеров.

## Правила изменений

- Исправление воспроизводимой ошибки должно получать regression test, если поведение можно изолировать.
- Тест должен проверять наблюдаемое поведение, а не внутреннее устройство метода.
- Изменения очереди обязаны сохранять at-least-once доставку и идемпотентность `EventId`.
- Изменения авторизации проверяются минимум для anonymous и всех затронутых ролей, включая чужую область данных.
- Изменения схемы проверяются на новой и уже существующей базе без удаления данных.
- Нельзя заявлять прохождение внешнего стенда, установщика или интеграционного сценария без фактического запуска.
