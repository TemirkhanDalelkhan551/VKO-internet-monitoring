# UX-разбор EXE, веб-панели и пользовательских сценариев

Дата анализа: 19.09.2026. Основание: ТЗ и презентация из истории проекта, текущие исходники, установщик 1.0.0, документация и опубликованная страница входа Render.

Это эвристическая оценка по реализации, а не результат наблюдения за реальными сотрудниками школ. Окончательные выводы о понятности нужно подтвердить короткими пользовательскими тестами на чистом компьютере.

Первая итерация по итогам разбора уже реализована в исходниках версии 1.1.0: двухшаговая проверка без расходования кода, подтверждение школы/линии/поставщика, проверка readiness и встроенный рабочий URL. Для выдачи нового EXE нужно опубликовать совместимый API, повторно собрать пакет и провести чистую установку.

## 1. Общая оценка

Основной сценарий уже целостный: администратор создаёт школу и линию, выдаёт одноразовый код, технический специалист запускает один EXE, активирует компьютер, после чего Windows-служба работает в фоне, а состояние появляется в веб-панели. Для демонстрации это понятный путь. Для пилота в школах не хватает доверия к EXE, предварительной диагностики, безопасного восстановления после неудачной активации и управления жизненным циклом устройств.

| Область | Оценка из 5 | Обоснование |
|---|---:|---|
| Первый запуск EXE | 3,5 | Один файл, русский интерфейс и автозапуск активации; нужны права администратора, файл не подписан |
| Понятность активации | 3,5 | Поля и подсказки ясные; адрес сервера приходится вводить вручную, до отправки нельзя проверить код и привязку |
| Ежедневная работа агента | 4 | Служба работает без участия пользователя, есть локальная панель состояния и история |
| Восстановление после ошибки | 2,5 | Есть сообщения об ошибках, но нет пошаговой диагностики, экспорта отчёта и управляемого отката активации |
| Массовое развёртывание | 2 | Нет тихой установки, централизованной конфигурации, подписанного обновления и реестра развёртываний |
| Понятность веб-панели | 4 | Вход, сводка, карта, карточки, отчёты и справочники логично связаны |
| Первичная настройка в веб-панели | 3 | Все функции есть, но нет единого мастера «школа → линия → код → проверка устройства» |
| Доступность и мобильность веб-панели | 3,5 | Есть подписи, focus-visible, мобильная компоновка и прокрутка таблиц; полноценная проверка клавиатурой и экранным диктором не зафиксирована |

## 2. Что уже есть в EXE

- Один self-contained установщик `VkoInternetMonitoringAgent-Setup-1.0.0-win-x64.exe`; отдельный .NET Runtime не нужен.
- Ограничение на Windows 10/11 x64 и запрос прав администратора.
- Установка или обновление Windows-службы с сохранением существующего `appsettings.json`.
- Русский мастер активации: адрес HTTPS-сервера, одноразовый код, название компьютера, кабинет и тип подключения.
- Проверка формата адреса, обязательности кода и названия компьютера.
- Одноразовая серверная активация с привязкой к школе и линии.
- Защита токена через DPAPI, ограничение доступа к его файлу, автоматический запуск службы.
- Локальная панель активированного компьютера: состояние связи и службы, последняя связь, пять метрик и 20 последних измерений.
- Автообновление локальной панели раз в минуту и ручная кнопка обновления.
- Ярлыки состояния, журнала и удаления в меню «Пуск».
- Повторная настройка с предупреждением о необходимости нового кода.
- Сохранение данных в `ProgramData` при удалении, чтобы случайное удаление программы не уничтожало диагностику и идентичность установки.

Проверенный файл имеет размер 37 253 782 байта, SHA-256 `4FAF4D2D1CB8A7264D7A53DBFA9E8B427508B143636D6399298DBE4DAE5DA955`, версию продукта 1.0.0 и сейчас не имеет цифровой подписи.

## 3. Что нужно доделать в EXE

### P0 — перед установкой на реальные школьные компьютеры

1. Подписать установщик и исполняемые файлы сертификатом подписи кода с timestamp. Без этого Windows SmartScreen и антивирус создают самый высокий порог доверия.
2. Провести чистую установку на втором физическом ПК: новая установка, UAC, активация, перезагрузка, первый heartbeat, первый замер, временное отсутствие сети, восстановление очереди и удаление.
3. Добавить экран предварительной проверки до использования кода: версия и разрядность Windows, права администратора, доступность API, TLS, свободное место, возможность создать/запустить службу и доступность измерительных endpoints.
4. Убрать ручной ввод рабочего адреса сервера из обычного сценария. Адрес следует встроить в официальный пакет или передавать отдельным подписанным профилем; поле оставить в расширенных настройках.
5. Перед окончательной активацией показать подтверждение: название школы, линия, поставщик и срок действия кода. Сейчас пользователь узнаёт только результат регистрации, а не проверяет выбранный объект до изменения.
6. Сделать завершение установки транзакционным с точки зрения пользователя. Сервер уже расходует код до сохранения локальной конфигурации и запуска службы; при локальном сбое возникает зарегистрированное, но неработающее устройство и нужен новый код.
7. После успеха показать простой финальный экран: «служба работает», «сервер видит компьютер», «последняя связь», кнопки «Открыть состояние» и «Скопировать технический отчёт». Один Device ID без названия школы мало помогает обычному пользователю.
8. Добавить понятные категории ошибок и действия: сервер недоступен, код неверен/истёк/использован, служба не запускается, сертификат сервера отклонён, конфигурация повреждена, токен отозван.

### P1 — для пилота

- Экспорт диагностического пакета без секретов: версия, состояние службы, последние журналы, результат проверки API и идентификатор устройства.
- Кнопки «Проверить связь», «Перезапустить службу» и «Открыть журнал» в локальной панели.
- Явное состояние «агент работает, но первого замера ещё не было» с ожидаемым временем следующего замера.
- Отображение версии агента и статуса обновления.
- Безопасный сценарий «заменить компьютер» и «перепривязать к другой линии» вместо общей повторной активации.
- Корректная очистка или осознанное сохранение `ProgramData` при удалении через отдельный выбор с объяснением последствий.
- Тихая установка для администратора домена/Intune/GPO с заранее заданным URL, журналом результата и ненулевым exit code при сбое.
- Подписанные обновления, канал версии и возможность контролируемого отката.

### P2 — для промышленной эксплуатации

- Централизованное развёртывание и инвентаризация версий.
- Удалённая конфигурация расписания и порогов с аудитом.
- Контроль целостности пакета и опубликованный checksum рядом со скачиванием.
- Поддержка прокси при подтверждённой необходимости и отдельная сборка x86 только если инвентаризация обнаружит 32-битные ПК.

## 4. Основные пользовательские сценарии

### Сценарий A. Подключение новой школы

1. Региональный оператор или администратор входит в веб-панель.
2. Создаёт или проверяет школу, контакт ответственного и координаты.
3. Создаёт основную линию, указывает поставщика, договор и тариф.
4. Выдаёт одноразовый код с разумным сроком, например 30–60 минут.
5. Передаёт специалисту официальный EXE, адрес сервера и код по согласованному каналу.
6. Специалист запускает EXE с правами администратора и подтверждает школу/линию.
7. Установщик проверяет запуск службы и первую связь с сервером.
8. Веб-панель показывает новое устройство и время heartbeat.
9. Оператор фиксирует успешное подключение; после первого измерения проверяет метрики.

Сейчас шаги 1–6 и серверная часть шага 8 реализованы. Нет единого контрольного списка, подтверждения привязки до активации и гарантированной проверки первого heartbeat в мастере.

### Сценарий B. Обычная ежедневная работа

1. Агент запускается с Windows и отправляет heartbeat.
2. В запланированные окна выполняет замеры, не мешая пользователю при высокой нагрузке.
3. При отсутствии API сохраняет события локально и отправляет позже.
4. Школьный пользователь видит только свою школу; район, область и поставщик видят разрешённую область.
5. При устойчивом ухудшении появляется инцидент.

Этот сценарий реализован хорошо. Пользователю нужно яснее объяснить разницу между «агент на связи», «интернет в норме» и «последний замер устарел».

### Сценарий C. Неверный или просроченный код

1. Мастер сообщает, что код неверен, просрочен или уже использован.
2. Введённые название компьютера и кабинет сохраняются.
3. Пользователь получает новый код у администратора и повторяет попытку.

Сообщение реализовано, но все три причины объединены. Веб-панель не показывает реестр кодов, поэтому администратор не может проверить статус конкретного кода или отозвать его.

### Сценарий D. Сервер или интернет недоступен во время установки

1. Предварительная проверка отличает отсутствие интернета от недоступности API и ошибки TLS.
2. Код не расходуется до готовности локальной части.
3. Пользователь получает конкретное действие и может повторить попытку.

Сейчас HTTP-клиент имеет таймаут 30 секунд, но отдельной проверки и понятной классификации сетевой ошибки нет.

### Сценарий E. Замена или переустановка компьютера

1. Оператор выбирает старое устройство в веб-панели.
2. Нажимает «Заменить устройство», блокирует старый токен и выдаёт код для нового ПК.
3. Новый компьютер активируется на той же школе и линии.
4. История старого устройства сохраняется, а в интерфейсе видна связь замены.

API умеет блокировать устройство и ротировать токен, но в веб-панели нет экрана управления устройствами и отдельного процесса замены.

### Сценарий F. Перевод на другую линию или смена поставщика

Нужно заранее определить, создаётся ли новая регистрация устройства, меняется привязка существующей или сохраняется отдельная история по периодам действия линий. Сейчас общая «повторная настройка» не объясняет эту бизнес-семантику.

### Сценарий G. Удаление агента

1. Специалист удаляет агент стандартным деинсталлятором.
2. Служба останавливается и удаляется.
3. Система спрашивает, сохранить ли локальные данные для переустановки.
4. Веб-панель помечает устройство как выведенное из эксплуатации или оператор делает это вручную.

Сейчас служба удаляется, а `ProgramData` сохраняется. Сервер не получает событие вывода из эксплуатации, и для пользователя это поведение не объяснено.

## 5. Веб-панель: что удобно

- Чёткая русская страница входа и объяснение ролевого доступа.
- Одна сводка объединяет школы, статусы, свежесть и присутствие агента.
- Основные и резервные линии показаны отдельно.
- Карта, таблица и фильтры используют одну область данных.
- Карточка школы связывает контакты, линии, устройства, историю и инциденты.
- Код активации выдаётся в контексте выбранных школы и линии; есть срок, копирование и автоматическое скрытие после истечения.
- Отчёты CSV/XLSX строятся по серверным данным и учитывают область роли.
- Элементы форм имеют подписи, сообщения используют live/status области, есть видимый keyboard focus.
- Интерфейс адаптирован к узкому экрану; широкие таблицы прокручиваются внутри контейнера.

## 6. Веб-панель: что улучшить

### P0/P1

1. Добавить стартовый мастер администратора: «создать школу → добавить линию → выдать код → дождаться компьютера → увидеть первый замер».
2. Сделать отдельный экран устройств: версия агента, последнее соединение, последний замер, линия, состояние токена, блокировка, замена и вывод из эксплуатации.
3. Добавить реестр кодов без показа секретного значения: школа, линия, создатель, время, срок, статус `действует/использован/истёк/отозван` и действие «отозвать».
4. После выдачи кода показывать короткую пошаговую инструкцию и кнопку копирования всего набора: URL сервера, код, срок и checksum EXE.
5. Развести термины визуально и текстом: качество последнего замера, свежесть данных, heartbeat агента и открытый инцидент — четыре независимых состояния.
6. Добавить first-run и пустые состояния с конкретным следующим действием. Например, если школ нет — «Создать школу», если нет линии — «Добавить линию», если нет устройств — «Выдать код».
7. Опубликовать текущий интерфейс инцидентов на Render и провести сквозную приёмку ролями на рабочем стенде.
8. Реализовать веб-экраны пользователей и аудита, иначе персональная авторизация технически есть, но администратор не может полноценно управлять ей из продукта.
9. Провести формальную проверку доступности: только клавиатура, масштаб 200%, контраст, NVDA, мобильные формы и карта.
10. Добавить справку «Что означает статус?» и ссылку на диагностику из карточки проблемного устройства.

### P2

- Сводки по районам и поставщикам, уведомления и правила эскалации.
- Обращение поставщику с редактируемым AI-черновиком и обязательным подтверждением человеком.
- Плановые работы, подавление уведомлений и объединение связанных инцидентов.
- PDF при наличии реального получателя и утверждённого шаблона.

## 7. Пороги входа

| Порог | Для кого | Как снизить |
|---|---|---|
| Права локального администратора | Школьный специалист | Заранее указать требование, дать чек-лист или централизованное развёртывание |
| SmartScreen из-за отсутствия подписи | Любой установщик | Подписать EXE; не обучать пользователей обходить предупреждение |
| Ручной URL сервера | Неспециалист | Встроить URL в рабочий пакет и оставить расширенную настройку отдельно |
| Координация двух людей: администратор панели и специалист у ПК | Организация | Код с понятным сроком, готовая инструкция и подтверждение подключения в панели |
| Термины «линия», «устройство», «heartbeat», «последний замер» | Школа/район | Единый словарь, подсказки и человекоориентированные названия |
| Бесплатный Render может просыпаться десятки секунд | Первый установщик | Перед выдачей кода проверять readiness, показывать «сервер запускается» и повторять безопасно |
| Прокси, фильтрация HTTPS, антивирус | Школьная сеть | Preflight с точными доменами/портами и диагностический отчёт |
| Неясный владелец процесса | Все роли | Назначить, кто создаёт школу, кто ставит агент, кто подтверждает первый замер и кто закрывает инцидент |

## 8. Вопросы, не определённые в ТЗ

До пилота нужно принять и записать решения по следующим вопросам:

- Кто является владельцем установки и имеет локальные права администратора в школе?
- На каком физическом ПК ставится агент и должен ли он быть постоянно включён?
- Что считается одной точкой мониторинга: школа, здание, линия или конкретный компьютер?
- Что делать при нескольких корпусах, нескольких основных линиях, Wi-Fi и проводном подключении одновременно?
- Как обрабатывать сон, гибернацию, выключение ПК и каникулы, чтобы не считать их аварией интернета?
- Как учитывать VPN, прокси, captive portal, контент-фильтрацию и смену маршрута между интерфейсами?
- Что происходит при переименовании/слиянии школы, смене района, поставщика, тарифа или номера договора?
- Как различать плановые работы, аварию поставщика, отключение электричества и неисправность школьного оборудования?
- Когда код можно отозвать, сколько активных кодов разрешено и кто видит их историю?
- Как выводить устройство из эксплуатации, сохранять его историю и предотвращать ложные инциденты?
- Каков SLA heartbeat, замеров, реакции на инцидент и восстановления?
- По какому часовому поясу считаются сутки, сроки кода и отчёты; что делать с неверными часами на ПК?
- Каковы сроки хранения измерений, IP, контактов, инцидентов, аудита и локальных журналов?
- Кто делает резервные копии, как часто проверяется восстановление и каков допустимый простой?
- Кому и по каким каналам отправляются уведомления, что является эскалацией и как избежать спама?
- Какая версия агента минимально допустима и как выполняется обязательное обновление?
- Какая поддержка нужна пользователю: телефон, ответственный, диагностический файл и регламент реакции?
- Какие требования к локализации: только русский или также казахский?
- Какие реальные данные можно показывать поставщику и можно ли ему видеть контакты школы?
- Как подтверждаются координаты школ и договорные показатели, кто отвечает за их актуальность?

## 9. Рекомендуемая последовательность работ

1. Подписать EXE и провести полную чистую установку на втором ПК по фиксированному сценарию.
2. Добавить preflight и финальную проверку heartbeat в мастер, встроить рабочий URL.
3. Закрыть проблему частичной активации и добавить диагностический отчёт.
4. Сделать веб-мастер первичного подключения, реестр устройств и кодов.
5. Опубликовать и принять интерфейс инцидентов на Render.
6. Провести пять коротких usability-сессий, исправить повторяющиеся затруднения.
7. Добавить управление пользователями/аудитом, затем жизненный цикл устройства и подписанные обновления.
8. После пилота реализовывать уведомления, сводки, обращение поставщику и AI-черновик.

## 10. План пользовательской проверки

Достаточно пяти участников: администратор системы, региональный оператор, районный специалист, сотрудник школы и технический специалист по установке. Каждый выполняет задачу без устной подсказки; наблюдатель записывает время, ошибки и вопросы.

| Тест | Критерий успеха |
|---|---|
| Создать школу и линию | До 5 минут, без обращения к разработчику |
| Выдать код и объяснить его назначение | Пользователь понимает однократность, срок и привязку |
| Установить агент на чистый ПК | До 10 минут, без непонятных предупреждений и ручного редактирования файлов |
| Убедиться, что компьютер подключён | Пользователь находит heartbeat и отличает его от первого замера |
| Найти причину проблемного статуса | До 2 минут, корректно называет качество, свежесть и инцидент |
| Заменить компьютер | Старая история сохраняется, старый токен отозван, новый ПК появляется без дубля |
| Получить помощь при ошибке | Сообщение приводит к конкретному действию, диагностический отчёт формируется без секретов |

Минимальные продуктовые показатели пилота: не менее 90% успешных установок с первой попытки, медианное время подключения до 10 минут, отсутствие ручного изменения конфигурации, не более одного обращения в поддержку на десять установок и однозначное понимание четырёх состояний: служба, heartbeat, свежесть измерения и качество линии.
