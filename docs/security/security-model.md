# Модель безопасности

Документ описывает реализованные границы доверия и известные ограничения. Он не является формальной сертификацией безопасности. Реестр обрабатываемых данных и исторические проверки дополняют [SECURITY_AND_PRIVACY.md](../SECURITY_AND_PRIVACY.md).

## Защищаемые активы

- индивидуальные токены устройств и одноразовые коды активации;
- пользовательские пароли и session tokens;
- строки подключения, ключ AI provider и токен Telegram Bot;
- измерения, внешний IP, heartbeat и аппаратная инвентаризация;
- справочники школ, договорные и контактные данные;
- инциденты, комментарии, история устройств и аудит.

## Границы доверия

| Граница | Контроль |
| --- | --- |
| Устройство → API | HTTPS в рабочем контуре; `X-Device-Token`; одновременная проверка School ID, Device ID и Line ID; rate limit и ограничение тела запроса. |
| Браузер → API | Bearer-сессия, роль и область доступных линий; серверная авторизация независимо от видимости элементов UI. |
| API → PostgreSQL | Строка подключения из конфигурации/секретов среды; параметризованные операции Npgsql; база Render закрыта внешним `ipAllowList`. |
| API → AI provider | Необязательный HTTPS-клиент, отдельный API key и timeout; передаётся ограниченный набор фактов для черновика. |
| API → Telegram | Необязательный HTTPS-клиент, bot token из секрета и заданный список chat IDs. |
| Локальный setup → Windows-служба | Запуск с правами администратора, запись в ProgramData, DPAPI и ACL для SYSTEM/администраторов. |

## Аутентификация устройств

Каждое рабочее устройство получает случайный токен. PostgreSQL хранит SHA-256-хэш, а Windows-компьютер — DPAPI-защищённый файл. Сервер принимает служебные операции только при совпадении токена и всей привязки устройства. Блокировка, ротация, замена и списание отзывают доступ в соответствии с операцией.

Одноразовый код активации хранится как хэш, имеет срок действия и расходуется атомарно. Восстановительное повторное использование ограничено временем, тем же аппаратным идентификатором и активным устройством.

## Аутентификация и авторизация пользователей

Пароли хэшируются `PasswordHasher` ASP.NET Core Identity. Случайный session token возвращается пользователю один раз; в PostgreSQL сохраняется SHA-256-хэш. Web UI хранит токен только в памяти.

Роли `Administrator`, `Regional`, `District`, `School` и `Provider` проверяются сервером. Для ограниченных ролей API вычисляет доступные линии до чтения, изменения, лимита или агрегации. Чужой ресурс обычно скрывается ответом `404`, запрещённая операция возвращает `403`, отсутствующая или отозванная сессия — `401`.

Legacy `X-Admin-Token` поддерживается конфигурацией для bootstrap/совместимости, но в `render.yaml` отключён. Он не должен использоваться как основной пользовательский механизм.

## Защита входных данных и HTTP

- Доменные валидаторы проверяют идентификаторы, диапазоны, строки, временные интервалы и допустимые переходы состояний.
- Обычное тело запроса ограничено; speed upload имеет отдельный настраиваемый предел.
- Публичные speed endpoints, необходимые setup до активации, защищены отдельным IP rate limit и общим настраиваемым лимитом параллельных запросов.
- Отдельные политики rate limiting применяются к login, activation, agent read/write, admin read/write и speed test.
- Forwarded headers принимаются только от loopback proxy.
- Ответы выставляют CSP, `X-Content-Type-Options: nosniff` и `Referrer-Policy`.
- Каждый ответ содержит correlation ID; неожиданные ошибки скрываются за `ProblemDetails` без текста исключения и получают `traceId` для диагностики.
- Пользовательские ответы и аудит не должны содержать пароли, токены или тела запросов.
- CSV/XLSX-экспорт нейтрализует формулы из текстовых значений.

## Аудит

Защищённая пользовательская операция получает запись аудита до выполнения. Если начало аудита сохранить нельзя, изменение не выполняется. После запроса фиксируются HTTP-результат и время. Бизнес-операция и завершение записи аудита не образуют единую транзакцию, поэтому незавершённая запись означает попытку, а не подтверждённый успех.

## Данные внешних сервисов

AI provider получает название школы, линии и поставщика, номер, тип, описание и время инцидента, количество измерений и агрегированные Download/Upload/Ping/Jitter/Packet Loss. Запрос содержит `store: false`, но фактическая политика хранения зависит от выбранного провайдера и договора с ним.

Telegram получает название школы и линии, номер инцидента, источник, описание причины, время события и публичный URL панели. Индивидуальные измерения, IP и токен устройства в сообщение не включаются.

Обе интеграции выключены без явной конфигурации. Их секреты должны храниться вне Git.

## Известные ограничения

- Локальная файловая очередь агента не шифруется целиком.
- Установщик и исполняемые файлы не имеют доверенной цифровой подписи, пока не предоставлен сертификат.
- Сроки хранения измерений, IP, контактов, комментариев и аудита не автоматизированы.
- Telegram-очередь хранится в памяти и не гарантирует доставку при переполнении или перезапуске.
- Внешние зашифрованные резервные копии и централизованные логи/метрики не настроены кодом репозитория.
- EventId обеспечивает идемпотентность, но не является подписью запроса.
- Владелец PostgreSQL технически способен изменять аудит; отдельная защита от этого не реализована.
