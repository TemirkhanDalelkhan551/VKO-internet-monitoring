# API системы мониторинга

API реализовано на ASP.NET Core и использует JSON. Для пилотного и промышленного развёртывания требуется HTTPS/TLS. HTTP разрешён агентом только для loopback-разработки.

## Авторизация

Агент передаёт токен в заголовке `X-Device-Token`. В PostgreSQL хранится только SHA-256-хэш токена. Сервер одновременно проверяет Device ID, School ID, Line ID, токен и отсутствие блокировки устройства.

Административные методы текущего MVP используют заголовок `X-Admin-Token`. Это временный механизм до реализации пользователей и ролевой модели из ТЗ.

## Методы агента

### POST /api/measurements

Принимает измерение Download, Upload, Ping, Jitter, Packet Loss, длительность теста, фактический тип подключения, сервер измерения, состояние соединения, время и версию агента. Внешний IP не принимается на доверии от клиента: API устанавливает его по адресу входящего соединения. Повторный Event ID не создаёт вторую запись.

### POST /api/devices/heartbeat

Фиксирует последнюю связь зарегистрированного устройства и версию агента. Heartbeat не запускает тест скорости и не создаёт дополнительную сетевую нагрузку измерения.

### GET /api/devices/{deviceId}/status

Возвращает состояние и 20 последних измерений только запрашивающего устройства за семь дней. Требует `schoolId`, `lineId` и индивидуальный `X-Device-Token`; сервер одновременно сверяет все три идентификатора, токен и блокировку. Административный токен не используется, поэтому локальная панель не получает доступ к другим компьютерам.

### POST /api/devices/register

Требует `X-Admin-Token` и PostgreSQL. Создаёт или обновляет школу, линию и устройство. В ответе токен устройства возвращается один раз; в базе сохраняется только его хэш.

Этот метод предназначен для административного заполнения справочников. Установщик на школьном компьютере не должен получать административный токен.

### POST /api/activation-codes

Требует `X-Admin-Token` и PostgreSQL. Создаёт короткий одноразовый код для уже существующей связки школы и интернет-линии. Срок действия задаётся от 5 минут до 24 часов, по умолчанию 30 минут. Открытый код возвращается только в ответе; в базе сохраняется SHA-256-хэш.

### POST /api/devices/activate

Принимает одноразовый код, имя устройства, кабинет, тип соединения и необязательный аппаратный идентификатор. Сервер привязывает устройство только к школе и линии, указанным при создании кода, и возвращает индивидуальный токен устройства один раз.

Использованный, истёкший или неизвестный код отклоняется одинаковым ответом `401`. Количество попыток ограничено десятью в минуту для одного IP-адреса.

## Методы мониторинга

Все методы этого раздела требуют `X-Admin-Token`.

- `GET /api/schools` — список школ, количество и активность устройств, последняя метрика и текущий статус.
- `GET /api/schools/{schoolId}` — сводка выбранной школы.
- `GET /api/schools/{schoolId}/devices` — устройства школы, последняя связь, версия и последняя метрика.
- `GET /api/devices/{deviceId}/measurements` — история устройства. Поддерживает `from`, `to` и `limit`.
- `GET /api/analytics` — агрегаты за период. Поддерживает `schoolId`, `from` и `to`.
- `GET /api/measurements/recent` — последние принятые измерения для диагностики.
- `GET /api/incidents` — список инцидентов с фильтрами `schoolId`, `status`, `from`, `to` и `limit`.
- `GET /api/incidents/{incidentId}` — карточка инцидента с длительностью и историей автоматических событий.

Если период не указан, история устройства возвращается за последние 30 дней, а аналитика — за последние сутки.

## Автоматические инциденты

После сохранения каждого измерения API анализирует последовательность результатов для конкретной интернет-линии. По умолчанию инцидент создаётся после двух проблемных измерений подряд и переводится в `Resolved` после двух нормативных измерений подряд. Одиночное кратковременное отклонение игнорируется.

Условия настраиваются через `MonitoringApi:Incidents`: количество последовательных проблемных и успешных измерений, минимальная длительность нарушения и максимальный объём анализируемой истории. Для одной линии одновременно допускается только один незавершённый инцидент. Повторная отправка того же измерения не создаёт второй инцидент.

Автоматически заполняются уникальный номер, школа, линия, поставщик, тип и описание проблемы, время начала и обнаружения, последнее связанное измерение, время восстановления, текущая длительность и история событий. Ручные переходы по рабочим статусам и назначение ответственного будут добавлены вместе с пользователями и ролями.

## Правила текущего статуса

- `Normal` — последнее измерение находится в пределах всех порогов.
- `Unstable` — нарушен минимум один порог.
- `Critical` — агент сообщил `Degraded` либо показатель отклоняется от порога более чем в два раза.
- `NoConnection` — последнее измерение имеет состояние `Offline`.
- `Unknown` — измерений ещё нет.

Эти статусы описывают последнее измерение. Устойчивое нарушение по нескольким последовательным измерениям будет оформляться отдельным инцидентом на следующем этапе.

## Служебные методы

- `GET /health/live` — проверяет, что процесс API запущен и отвечает.
- `GET /health/ready` — проверяет готовность принимать данные, включая доступность PostgreSQL. Возвращает `503`, если база недоступна; медленный ответ базы помечается как `Degraded`.
- `GET /health` — совместимый короткий адрес для полной проверки готовности.
- `GET /speed/download` — контролируемая загрузка данных для локального теста скорости.
- `POST /speed/upload` — контролируемая отправка данных для локального теста скорости.

## Текущие ограничения

Автоматическое сохранение результата активации через DPAPI, графическая настройка и локальная панель состояния реализованы. Пользователи и роли, редактирование школ и линий, управление порогами, инциденты, уведомления, экспорт и аудит административных действий будут добавлены следующими этапами. До их реализации административный токен нельзя считать полноценной ролевой авторизацией.
