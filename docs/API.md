# API системы мониторинга

API реализовано на ASP.NET Core и использует JSON. Для пилотного и промышленного развёртывания требуется HTTPS/TLS. HTTP разрешён агентом только для loopback-разработки.

При работе через локальный Cloudflare Tunnel API принимает `CF-Connecting-IP` и
`X-Forwarded-Proto` только от loopback proxy. Cloudflare рекомендует
`CF-Connecting-IP`, потому что этот заголовок содержит ровно один исходный адрес
клиента. Заголовки от недоверенных сетевых клиентов игнорируются, чтобы исключить
подмену IP.

## Авторизация

Агент передаёт токен в заголовке `X-Device-Token`. В PostgreSQL хранится только SHA-256-хэш токена. Сервер одновременно проверяет Device ID, School ID, Line ID, токен и отсутствие блокировки устройства.

Пользователи входят через `POST /api/auth/login` с JSON `{"login":"...","password":"..."}`. Ответ содержит `accessToken`, `expiresAtUtc` и учётную запись. Далее передаётся `Authorization: Bearer <accessToken>`. Срок сессии задаёт `MonitoringApi:UserSessionLifetimeMinutes` (480 минут по умолчанию, допустимо 5–1440).

Пароли хэшируются стандартным `PasswordHasher` ASP.NET Core Identity; сессии в PostgreSQL содержат только SHA-256-хэш случайного токена. Пять неверных паролей блокируют вход в учётную запись на 15 минут; отдельно вход ограничен 10 запросами в минуту на IP. Ответы пользовательского API имеют `Cache-Control: no-store`. Клиент не должен записывать токен в URL или журналы; веб-интерфейс должен хранить его в памяти до выхода/истечения сессии.

`X-Admin-Token` оставлен только как отключаемый механизм первичного создания администратора/совместимости (`MonitoringApi:EnableLegacyAdminToken`). При включении он предоставляет полный доступ под автором `bootstrap-admin`. **На текущем рабочем экземпляре он отключён**; после создания первого администратора его нужно отключать и на других развёртываниях. Startup-конфигурация по-прежнему требует непустой `AdminToken`.

### Пользователи и сессии (PostgreSQL)

- `GET /api/auth/me` — текущая учётная запись.
- `POST /api/auth/logout` — отзыв текущей сессии.
- `POST /api/auth/password` — `currentPassword` и `newPassword`; успешная смена отзывает все прежние сессии.
- `GET /api/users` и `POST /api/users` — список и создание учётных записей; только администратор.
- `PUT /api/users/{userId}` — изменение `displayName`, `role`, области доступа и `isBlocked`; только администратор.
- `POST /api/users/{userId}/password` — административный сброс через `newPassword`; отзывает сессии и снимает временную блокировку входа, сохраняя `isBlocked`.
- `GET /api/audit?from=...&to=...&beforeId=...&limit=...` — журнал аудита, только администратор; курсор `beforeId`, максимум 1000 записей на ответ.

Создание пользователя принимает `login`, `displayName`, `password`, `role` и необходимую привязку. Логин — 3–64 латинских буквы/цифры и символы `._-`, регистр игнорируется. Пароль — 12–128 символов. Учётные записи не удаляются через API, поэтому история авторов сохраняется. Блокировка, изменение роли/привязки и смена пароля немедленно делают старые сессии недействительными; разблокировка их не восстанавливает. Нельзя заблокировать или понизить роль последнего активного администратора.

| Роль | Область данных | Изменения |
| --- | --- | --- |
| `School` | Все линии своей школы; обязательный `schoolId` | Создание ручного инцидента своей линии |
| `District` | Школы своего района/города; обязательный `districtCity` | Просмотр и анализ |
| `Regional` | Все школы и линии | Существующие административные операции, кроме управления пользователями и аудита |
| `Provider` | Только линии с указанным `providerName` | Статусы и комментарии своих инцидентов |
| `Administrator` | Все данные | Пользователи, устройства, инциденты и аудит |

Привязки района и провайдера сравниваются с текущими значениями справочников точно, с учётом регистра. Ограничения применяются до SQL-агрегации и лимита к школам, устройствам, последним замерам, истории, инцидентам и аналитике. Поставщик не видит чужую линию/её устройства и метрики в школе с двумя провайдерами; если доступная линия резервная, общая сводка основной линии остаётся пустой, а доступные показатели находятся в `lines`. Для чужих карточек/ресурсов возвращается `404`, запрещённой операции — `403`, отсутствующей или отозванной сессии — `401`.

### Аудит

До исполнения защищённого запроса сохраняются автор, User ID, метод/действие, путь без query string и IP. Затем записываются HTTP-результат и время завершения. Успешный вход привязывается к учётной записи; неудачный отмечается как `anonymous`. Ограничения частоты фиксируются отдельным событием `RateLimit`. Пароли, токены и тела запросов в аудит не попадают. Поле `actor` ручных операций инцидента заменяется сервером на логин из сессии (или `bootstrap-admin`).

Если начальная запись аудита недоступна, действие не выполняется. Запись результата и бизнес-изменение не являются одной транзакцией: при аварийном завершении после начальной записи в журнале может остаться попытка без `completedAtUtc` и `statusCode`. Такая запись требует проверки, а не считается успешным действием. Периодическая очистка истёкших сессий, срок хранения аудита и защита от изменений владельцем БД остаются эксплуатационными задачами.

## Методы агента

### POST /api/measurements

Принимает измерение Download, Upload, Ping, Jitter, Packet Loss, длительность теста, фактический тип подключения, сервер измерения, состояние соединения, время и версию агента. Внешний IP не принимается на доверии от клиента: API устанавливает его по адресу входящего соединения. Повторный Event ID не создаёт вторую запись.

Для состояния `Online` обязательны все пять метрик: Download, Upload, Ping, Jitter и Packet Loss. Значения могут быть ниже нормативов качества: это влияет на оценку качества, а не на успешность выполнения измерения. Для диагностических состояний `Offline` и `Degraded` допускаются отсутствующие метрики.

Дата измерения не должна превышать текущее серверное время более чем на `MonitoringApi:MaximumMeasurementClockSkewMinutes` (по умолчанию 5 минут; допустимые настройки 0–60). Старые результаты офлайн-очереди принимаются без ограничения давности. Нарушения этих правил возвращают HTTP `400` до записи измерения.

### POST /api/devices/heartbeat

Фиксирует последнюю связь зарегистрированного устройства и версию агента. Heartbeat не запускает тест скорости и не создаёт дополнительную сетевую нагрузку измерения.

### GET /api/devices/{deviceId}/status

Возвращает состояние и 20 последних измерений только запрашивающего устройства за семь дней. Требует `schoolId`, `lineId` и индивидуальный `X-Device-Token`; сервер одновременно сверяет все три идентификатора, токен и блокировку. Административный токен не используется, поэтому локальная панель не получает доступ к другим компьютерам.

### POST /api/devices/register

Требует `X-Admin-Token` и PostgreSQL. Создаёт или обновляет школу, линию и устройство. В ответе токен устройства возвращается один раз; в базе сохраняется только его хэш.

Этот метод предназначен для административного заполнения справочников. Установщик на школьном компьютере не должен получать административный токен.

### POST /api/activation-codes

Требует `X-Admin-Token` и PostgreSQL. Создаёт короткий одноразовый код для уже существующей связки школы и интернет-линии. Срок действия задаётся от 5 минут до 24 часов, по умолчанию 30 минут. Открытый код возвращается только в ответе; в базе сохраняется SHA-256-хэш.

### POST /api/devices/activate

Принимает одноразовый код, имя устройства, кабинет, тип соединения и необязательный аппаратный идентификатор. Сервер привязывает устройство только к школе и линии, указанным при создании кода, и возвращает индивидуальный токен устройства один раз.

Использованный, истёкший или неизвестный код отклоняется одинаковым ответом `401`. Количество попыток ограничено десятью в минуту для одного IP-адреса.

Запись агента ограничена 120 запросами в минуту на IP, а чтение локального
состояния — 60 запросами. Обычное тело API-запроса ограничено 256 КиБ.

## Администрирование устройств

Методы этого раздела требуют `X-Admin-Token`, PostgreSQL и ограничены 30
изменениями в минуту на IP.

### PUT /api/devices/{deviceId}/block-state

Принимает `{ "isBlocked": true }` или `{ "isBlocked": false }`. Заблокированный
компьютер не может отправлять heartbeat, измерения или читать своё
локальное состояние. Повторная установка того же состояния безопасна и
идемпотентна.

### POST /api/devices/{deviceId}/token/rotate

Отзывает прежний токен и возвращает новый 256-битный токен один раз.
В базе хранится только SHA-256-хэш. Ротация не разблокирует устройство: это
отдельное явное действие.

## Методы мониторинга

Все методы этого раздела требуют `X-Admin-Token`.

Административное чтение ограничено 120 запросами в минуту на IP,
административные изменения — 30 запросами.

- `GET /api/schools` — список школ, количество и активность устройств, последняя метрика и текущий статус.
- `GET /api/schools/{schoolId}` — сводка выбранной школы.
- `GET /api/schools/{schoolId}/devices` — устройства школы, последняя связь, версия и последняя метрика.
- `GET /api/devices/{deviceId}/measurements` — история устройства. Поддерживает `from`, `to` и `limit`.
- `GET /api/analytics` — агрегаты за период. Поддерживает `schoolId`, `from` и `to`.
- `GET /api/measurements/recent` — последние принятые измерения для диагностики.
- `GET /api/incidents` — список инцидентов с фильтрами `schoolId`, `status`, `from`, `to` и `limit`.
- `GET /api/incidents/{incidentId}` — карточка инцидента с длительностью и полной историей действий.
- `POST /api/incidents` — ручное создание инцидента для существующей связки школы и линии.
- `PUT /api/incidents/{incidentId}/status` — перевод по допустимому рабочему статусу.
- `PUT /api/incidents/{incidentId}/assignment` — назначение или снятие ответственного.
- `POST /api/incidents/{incidentId}/comments` — добавление комментария в историю.

Если период не указан, история устройства возвращается за последние 30 дней, а аналитика — за последние сутки.

## Автоматические инциденты

После сохранения каждого измерения API анализирует последовательность результатов для конкретной интернет-линии. По умолчанию инцидент создаётся после двух проблемных измерений подряд и переводится в `Resolved` после двух нормативных измерений подряд. Одиночное кратковременное отклонение игнорируется.

Условия настраиваются через `MonitoringApi:Incidents`: количество последовательных проблемных и успешных измерений, минимальная длительность нарушения и максимальный объём анализируемой истории. Для одной линии одновременно допускается только один незавершённый инцидент. Повторная отправка того же измерения не создаёт второй инцидент.

Автоматически заполняются уникальный номер, школа, линия, поставщик, тип и описание проблемы, время начала и обнаружения, последнее связанное измерение, время восстановления, текущая длительность и история событий.

Ручно инцидент проходит контролируемый маршрут: `New` → `SentToProvider` →
`InProgress`/`WaitingForInformation` → `Resolved` → `Closed`. Из `Resolved` его можно
вернуть в `InProgress`, если проблема возобновилась. Недопустимый переход
возвращает `409`. Даты передачи поставщику, восстановления и закрытия
фиксируются сервером. Назначения, комментарии и переходы статусов попадают в единую
историю. Поле `actor` определяет сервер по учётной записи пользователя; значение клиента игнорируется.

## Правила текущего статуса

- `Normal` — последнее измерение находится в пределах всех порогов.
- `Unstable` — нарушен минимум один порог.
- `Critical` — агент сообщил `Degraded` либо показатель отклоняется от порога более чем в два раза.
- `NoConnection` — последнее измерение имеет состояние `Offline`.
- `Unknown` — измерений ещё нет, последний замер просрочен, устройство заблокировано либо линия отключена.

`qualityStatus` сохраняет оценку последнего замера независимо от давности. `measurementFreshness` принимает `Missing`, `Fresh` или `Stale`; срок актуальности задаёт `MonitoringApi:MeasurementFreshnessMinutes` (по умолчанию 1440 минут, граница включительно). Доставка старого замера из офлайн-очереди не делает его актуальным.

`agentPresence` отдельно показывает `NotSeen`, `Active`, `Inactive` или `Blocked`. Окно активности задаёт `DeviceActiveWindowMinutes`; отсутствие heartbeat само по себе не означает отсутствие интернета. Статус качества и наличие связи с агентом нужно показывать отдельно.

Ответы списка и карточки школы содержат `lines` со сводками каждой основной, резервной и отключённой линии. Поля сводки школы и `primaryLineId` относятся к одной основной линии (`Primary`); резервная линия её не подменяет. Если основных линий несколько, выбирается первая по GUID; если их нет, сводка имеет `Unknown` и пустую метрику. Для остальных линий интерфейс должен использовать `lines`.

Устойчивые нарушения оформляются отдельными автоматическими инцидентами по настроенным последовательностям замеров.

## Служебные методы

Координаты школ: `latitude` и `longitude` возвращаются в списке/карточке школы. `PUT /api/schools/{schoolId}/location` принимает обе координаты либо обе NULL для удаления; доступен администратору и областному оператору с PostgreSQL, с аудитом. Подробнее: `WEB_MAP.md`.

- `GET /health/live` — проверяет, что процесс API запущен и отвечает.
- `GET /health/ready` — проверяет готовность принимать данные, включая доступность PostgreSQL. Возвращает `503`, если база недоступна; медленный ответ базы помечается как `Degraded`.
- `GET /health` — совместимый короткий адрес для полной проверки готовности.
- `GET /speed/download` — контролируемая загрузка данных для локального теста скорости.
- `POST /speed/upload` — контролируемая отправка данных для локального теста скорости.

## Текущие ограничения

Автоматическое сохранение результата активации через DPAPI, графическая настройка, локальная панель состояния, ручной жизненный цикл инцидентов, учётные записи, пять ролей и аудит API реализованы. Веб-панель содержит обзор, карточку школы, историю, карту и CSV/XLSX. Administrator/Regional создают и редактируют школы, контакты, линии и реквизиты договоров через POST/PUT `/api/schools` и `/api/schools/{schoolId}/lines`; подробнее `WEB_DIRECTORY.md`. Выдача кодов через веб-панель уже опубликована; UI инцидентов готов и проверен локально (WEB_INCIDENTS.md). Следующие этапы — публикация UI инцидентов, веб-экраны пользователей/аудита, управление порогами и уведомления. Приёмка на дополнительных физических компьютерах ещё предстоит.

## Справочники и веб-инциденты

- POST /api/schools и PUT /api/schools/{schoolId}: name, districtCity, address, responsibleName, responsiblePosition, responsiblePhone, responsibleEmail. Координаты изменяются отдельным PUT location.
- POST /api/schools/{schoolId}/lines и PUT /api/schools/{schoolId}/lines/{lineId}: name, providerName, connectionType, contractedDownloadMbps, contractedUploadMbps, contractNumber, contractDate, lineStatus. Школа и линия сохраняют идентификаторы; устройства и история не пересоздаются.
- Изменения справочников разрешены Administrator/Regional, проходят валидацию и аудит. PostgreSQL обязателен; файловый режим возвращает 501.
- Веб-интерфейс инцидентов использует прежние защищённые методы API. School создаёт инцидент своей линии; Provider комментирует/меняет статус своих инцидентов; Administrator/Regional также назначают ответственного; District читает. Actor задаёт сервер независимо от клиентского значения.
- Список инцидентов фильтруется по startedAtUtc (from включительно, to исключительно), schoolId и status; UI запрашивает limit=1000 и предупреждает при достижении лимита. Подробности — WEB_INCIDENTS.md.

Текущее состояние исходников и опубликованного сервера: PROJECT_SNAPSHOT.md.
